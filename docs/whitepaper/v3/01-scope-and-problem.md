## 0. 用途与标注规则

本文回答三个问题：新版白皮书研究什么、不研究什么；所研究的问题为何真实存在；后续阶段用什么证据和方法回答它。本文不是白皮书正文，也不给出协议的最终设计。

主张按下表标注，后续阶段沿用：

| 标注 | 含义 | 可接受的证据 |
| --- | --- | --- |
| [A] 学术结论 | 由经核验的原始文献支持，注明适用前提 | 原文，不含摘要与二手综述 |
| [E] 工程验证 | 在固定版本与环境中实际执行过的测试、实验或生产观测 | 运行记录与原始数据。本项目目前没有本轮可用的此类证据 |
| [C] 代码事实 | 固定基线的源码确实如此实现 | 提交号、文件与行号。它说明代码做了什么，不说明某项性质已经成立 |

## 3. 问题定义

### 3.1 非形式陈述

一组设备由个人控制、间歇连接、能力各异，一个 Agent 会话的执行可以在回合边界从一台设备转到另一台。研究问题是：在没有常驻中心协调者的条件下，系统应以什么机制、在什么假设下保证会话执行始终有明确定义？具体包括：同一时刻只有一台设备推进它；已经提交的事实不丢失；续跑不重复；工具的外部效果不被静默重复或遗漏。同时，原执行设备离线时用户仍能继续工作，而且用户对“任务在哪里执行”的理解不超出系统实际掌握的信息。

### 3.2 模型草图（阶段三给出完整定义）

- **节点**：Space 成员集合 N；可执行子集 X ⊆ N，即具备 `runtime.execute` 能力与 Core 版本的节点。
- **事实日志**：会话 k 的持久事实集合 F(k)，元素包括用户消息、assistant 段、工具调用与工具结果，每条事实具有不可变身份。节点 n 持有副本 Fₙ(k)，在消息最终送达的假设下趋同。
- **位置记录**：Binding b(k) = (owner, gen)。节点 n 持有本地视图 bₙ(k)，经同步或即时安装更新。
- **回合边界**：β(n, k) 成立，当且仅当 n 对 k 没有在途模型请求，且 n 上一轮产生的全部工具结果已持久化在 Fₙ(k) 中。
- **执行步**：e = (n, k, g, H)，表示节点 n 在本地视图代次 g 下、以历史 H 为输入，为会话 k 发出一次模型请求。

待研究的性质：

| 编号 | 性质 | 非形式定义 |
| --- | --- | --- |
| S1 | 代次内单一推进 | 对任意 (k, g)，代次 g 的全部执行步由同一节点发出 |
| S2 | 交接互斥 | 代次 g+1 的首个执行步发生之前，代次 g 的持有者已经持久地让出 g；让出之后，它不再以 g 发出执行步或提交事实 |
| S3 | 边界事实完整 | 代次 g+1 首个执行步所用的 H，包含代次 g 在让出前提交的全部事实 |
| S4 | 续跑至多一次 | 对任意 (k, g)，目标节点至多启动一次续跑；重试与重复消息不改变这一点 |
| S5 | 效果可判定 | 恢复后，每个有外部效果的工具调用都可判定为“未开始”“已完成且结果已记录”或显式的“未知”；系统不会自动重做“未知”状态下的不可幂等调用 |
| L1 | 可接管 | 原执行节点长期不可达时，用户可以在可达且具备能力的节点上继续该会话 |
| U1 | 位置可解释 | 节点 n 向用户展示的执行位置等于 bₙ(k).owner，并标明该信息是否已经得到对端确认 |

S1 与 S2 合起来，才保证任一时刻至多一个节点推进会话 k。

### 3.3 已知的理论张力 [T，阶段三给出精确陈述与论证]

1. **接管与单一推进。** 纯异步模型中，节点无法区分“原执行节点已崩溃”与“原执行节点仍存活但被分区”。这种不可区分性是异步系统多项不可能性结果的核心论证手段，例如 FLP [待核验] 与 Gilbert–Lynch 对 CAP 的证明 [待核验]。因此，只要原执行节点可能仍在运行，L1 与 S1、S2 就不能无条件同时成立。移动 Agent 文献处理同一张力的做法，是把每个执行阶段建模为一次共识，依靠多数正确的见证节点同时获得非阻塞与 exactly-once [待核验：Pleisch & Schiper]。依赖多数派的方案在只有两台设备的空间里无法容忍任何一台失效。
2. **租约的代价。** 在有界时钟漂移假设下，租约可以同时满足 S1 与 L1，代价是接管延迟 [待核验：Gray & Cheriton]。但租约只能约束“开始执行步”与“提交事实”，无法收回租约到期前已经开始的外部效果。移动平台会挂起进程，这使“每个执行步开始前检查租约”更为必要。
3. **隔离令牌的落点。** 隔离令牌要求被访问的资源检查令牌 [待核验：Chubby 的 sequencer]。外部模型服务与第三方 API 不会检查 Operit2 的代次，所以隔离只能由运行时自己实施：在每个执行步之前、每次提交事实之时检查，并在合并事实时识别过期代次产生的分叉。
4. **项目约束。** 架构文档明确不引入 Lease、Placement 等概念（`docs/core-node-space-binding-architecture.md:34-35`）。阶段三的协议设计必须说明是否违背这一约束；若不违背，要给出把相应语义并入 Binding 代次的等价表达。

### 3.4 LLM Agent 特有的两点 [T，阶段二确认新颖性]

1. **为什么交接点选在回合边界。** 在途的模型请求无法重放：输出不确定，会消耗配额。远程 Provider 的解码状态（KV cache）在服务端，运行时看不到；本地推理的解码状态虽然在本机，当前接口也没有暴露（2.0 §5.2，待在新基线复核）。数据中心内的请求迁移需要共享权重和可访问的 KV cache [待核验：Llumnix]，单机内的生成快照依赖本地解码状态 [待核验：AIOS]，两者都不适用于远程 Provider。回合边界上没有在途请求，工具结果已经持久化，Agent 的控制状态完全外化为事实日志与有界配置。这接近移动代码文献中的“弱迁移”：不迁移执行状态，在预定义点以迁移来的数据重新开始执行 [待核验：Fuggetta、Picco 与 Vigna 的定义原文]。两端运行同一份运行时代码，因此连代码也不需要迁移。
2. **数据一致不等于信念一致。** 事实日志可以完整交接，但其中包含关于执行环境的陈述，例如终端会话已打开、开发服务器正在运行、某文件刚被修改、浏览器停在某个页面。这些陈述在源端为真，到目标端可能为假。目标端的模型若不知道环境已经改变，就会基于失效的信念继续行动。移动代码文献把迁移单元对资源的绑定分为若干类，并讨论迁移时如何重新绑定或解除绑定 [待核验：Fuggetta 等]。LLM 会话的资源绑定隐含在自然语言上下文中，运行时无法逐条改写，只能检测并告知模型。因此，续跑正确性除了 S1–S5 这些数据与执行性质，还应包括一条“信念—环境一致性”：上下文中的环境陈述与目标环境一致，或者模型已被告知两者不一致。[C] 当前 `switch_core` 的工具说明没有告诉模型哪些资源不随迁移（`core/crates/provider/services/src/chat/config/SystemToolPrompts.rs:842-851, 882-885`）；目标端是否注入环境变化提示，尚未核实。

| --- | --- | --- |
| X1 | 源端在提交 Binding **之前**就释放了本地执行保护（`MessageProcessingDelegate.rs:987-994, 2669-2675`），而发送入口只以本地执行保护作互斥（`MessageCoordinationDelegate.rs:373, 664`；`ChatTurnTransport.rs:101`）。此时源端本地 Binding 仍指向自己。若用户在切换期间于源端发送新消息，新回合可能在源端开始，而目标端以不含该消息的传入历史续跑 | S2、S3 |
| X2 | 由非执行节点 C 发起 `changeChatExecutionDevice`。该方法未带路由注解，按设计文档 §6 的规则应在 C 本地执行（待核实）。于是比较写入发生在 C 的本地存储，并即时安装到目标 D；原执行节点 A 只收到一次瞬时的 `beforeChangeRoute` 探测，视图要等同步后才更新。A 上本地发起的请求仍可能在 A 执行，与 D 并发 | S2 |
| X3 | 交接生命周期调用的目标是 `CORE_INTERNAL_TARGET`，不在禁止重提之列（`RuntimeRemoteLinkService.rs:1134-1166`；`route_forwarding.rs:82-86`）。在存在多条路径的拓扑中，若 `AfterChangeRoute` 已经送达而响应丢失，转发层可能经另一首跳重提并再次触发续跑。第一次续跑仍在运行时，本地执行保护会拒绝第二次；第一次续跑已结束时，由于没有 (k, g) 去重，第二次续跑可能重复模型请求与工具调用。`AfterChangeRoute` 是否等待整个续跑结束，待核实 | S4、S5 |
| X4 | 两个节点基于同一条旧记录 (A, g) 并发比较写入，触发方式包括在不同节点上并发调用 `changeChatExecutionDevice`，或 owner 资料缺失时多个节点调用 `claimMissingBindingLocal`。结果是 owner 不同、代次同为 g+1 的两条记录。同步后冲突规则保留其中一条，但两侧在同一代次下已经发生的执行与外部效果不会撤销。这也说明当前的代次不能作为全网唯一的执行身份 | S1、S5 |
| X5 | 续跑使用源端传入的历史，而不是目标端的持久副本；提交前同步有页数上限，也不校验水位。若同步没有覆盖全部相关原文（例如超出页数上限、owner 未就绪），目标端模型所见历史可能与目标端持久副本暂时不一致。这不一定丢失事实，但目标端无法自行验证“续跑所需事实已经齐备”，界面显示的历史也可能落后于模型实际使用的历史 | S3、U1 |

## 5. 初步新颖性检查

> **阶段二修订：** 系统检索找到了多个 2025–2026 年的跨设备 Agent 系统与单机检查点研究，本节结论已收窄，见 [02-literature.md](02-literature.md) §4–§5。

本节只回答“这个问题是否已有研究”，不是阶段二的系统综述。检索日期为 2026-11-10；只读了检索结果与摘要，没有读全文。

| 相关方向 | 代表工作（存在性已初步确认） | 与本问题的关系 |
| --- | --- | --- |
| 移动 Agent 的 exactly-once 与非阻塞执行 | Rothermel & Straßer（SRDS 1998）；Pleisch & Schiper（SRDS 2000；IEEE TC 2003） | 最接近的理论先例：用观察者或见证节点与每阶段共识获得 exactly-once。假设服务器型主机，不涉及 LLM 调用与用户在环 |
| 代码迁移分类 | Fuggetta、Picco & Vigna（IEEE TSE 1998） | 强迁移与弱迁移的区分，以及迁移单元的资源绑定，可用来刻画回合边界续跑 |
| LLM 推理请求迁移 | Llumnix（OSDI 2024） | 在数据中心实例间迁移带 KV cache 的在途请求，需要共享权重与可访问的解码状态 |
| Agent 运行时的上下文快照 | AIOS（arXiv:2403.16971） | 单机内暂停与恢复生成，不处理跨设备的所有权 |
| 边缘 Agent 放置与迁移 | arXiv:2508.03345 | 在运营方控制的边缘服务器间迁移 Agent，优化成本与时延，不处理所有权安全 |
| 工具调用事务化 | Atomix（arXiv:2602.14849） | 把工具调用作为事务处理；作者声明不涉及分布式部署与完整的崩溃安全 exactly-once |
| 跨设备会话延续 | 若干产品页与博客 | 无同行评审，只作为问题存在的旁证，不作为技术依据 |

初步判断：已有研究分别覆盖了移动计算中的 exactly-once、数据中心内的请求迁移、单机 Agent 快照和工具事务。这次有限的检索没有找到同时处理“个人设备、无中心协调者、LLM 回合边界、外部效果、用户可解释性”的工作。这个判断需要阶段二的系统检索确认；确认之前，白皮书不使用“首个”一类表述。

## 7. 验证路径与约束

- **无需构建：** 静态审查、形式化建模与模型检查。模型检查需要安装并运行检查器（例如 TLA+ 的 TLC 需要 Java），不涉及项目构建；是否运行由 D4 决定。
- **需要授权构建：** 故障注入、多进程或多设备实验。仓库已有多进程压力运行器和带故障注入的契约测试（2.0 §11.1，C38），可以作为起点。按 AGENTS.md，每次运行前单独确认。
- **设计约束：** 协议不得在源端可达的常见路径上增加用户确认步骤；不引入静默回退，接管必须显式；遵守架构文档“不引入 Lease、Placement 等概念”的约束，若无法遵守，则明确说明并请求例外。

## 8. 自审

以下从独立审稿人的视角检查本阶段的结论。

1. **这是研究问题，还是实现缺陷？** 如果只是“缺少一处检查”，不足以支撑一篇研究型白皮书。贡献必须是可推广的模型、协议与取舍分析，Operit2 是案例与实现载体。§3.3 的张力不依赖 Operit2 的具体代码，这是把它当作研究问题的主要理由。
2. **更简单的替代方案。** “源端不可达就拒绝接管”可以平凡地满足 S1、S2，代价是放弃 L1；“引入中心服务器”违背项目前提。协议设计必须与这两个基线比较，说明增加的复杂度换来了什么。
3. **新颖性风险。** 闭源产品可能已有类似的交接机制，只是没有发表。新颖性主张只能限于分析、协议与验证方法，不能是“首个跨设备 Agent”。
4. **证据风险。** X1–X5 是静态推导，可能被尚未发现的防护阻止。在模型检查与代码复核之前，正文不得把它们写成缺陷。
5. **基线漂移。** 三天内有 45 个提交。正文必须冻结在一个提交上，并在每条 [C] 主张中注明。
6. **模型保真度。** 形式模型是对代码的抽象，需要附抽象映射表，说明哪些代码路径被合并或省略；否则模型检查的结论无法回指代码。
